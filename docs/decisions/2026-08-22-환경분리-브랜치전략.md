# 결정 — 환경 축 브랜치 전략 도입, DB 분리는 단계적으로 (2026-08-22)

> ⚠️ **§1 부분 번복 (2026-08-31).** 아래 §1 의 *"작업 브랜치는 `feat/…`·`fix/…`·`docs/…`"* 와 *"작업자 이름 브랜치 폐지"* 는 **사람 단위 개인 브랜치(`dev-jeongwon`·`dev-hanna`)로 되돌려졌다** — 근거 [[2026-08-31-개인-브랜치-복귀]]. squash 규칙도 함께 사라졌다(모든 병합이 merge commit).
> **나머지는 전부 유효하다** — 환경 축 `main`/`stg`/`dev` · dev 미배포 · Vercel 1프로젝트 2스코프 · DB 분리 보류. 이 문서가 여전히 그것들의 정본이다.

## 배경 — 검증 단계가 없었고, 프리뷰가 운영 DB를 쓴다

배포 스택은 Vercel Hobby 1개 프로젝트 + Supabase Free 1개 프로젝트다. 여기서 두 가지가 겹쳐 있었다.

1. **브랜치가 작업자 이름(`jeongwon`·`hanna`)으로 나뉘어 있었다.** 장수 브랜치를 재사용하며 PR을 49번 올렸고, "어디까지 검증된 코드인가"를 브랜치가 표현하지 못했다. `main` 머지 = 즉시 운영 배포인데 그 앞에 아무 단계가 없었다.
2. **프리뷰 배포가 운영 Supabase·운영 API 키를 그대로 쓴다.** [deploy-runbook](../deploy-runbook.md) §2에 경고로 적혀 있던 상태 — "프리뷰에서 만든 데이터가 실 DB에 쌓이므로 파괴적 테스트는 주의".

코드에도 환경 축이 없었다. `VERCEL_ENV`/`APP_ENV` 참조가 0건이고 `NODE_ENV`만 썼는데, Vercel 프리뷰도 `NODE_ENV=production`이라 **코드가 프리뷰와 운영을 구별하지 못했다.**

## 결정 — 브랜치 축을 먼저, 데이터 격리는 나중에

두 문제를 한꺼번에 풀 수도 있었지만 **비용 구조가 다르다.** 브랜치 재편은 되돌리기 쉽고 저장소 안에서 끝나는 반면, DB 분리는 새 Supabase 프로젝트·환경변수 이관·무료 한도 재배분이 걸린 인프라 작업이다. 그래서 순서를 나눴다.

### 1. 브랜치는 작업자가 아니라 환경으로 나눈다 (지금 적용)

`main`(=prd, 보호) · `stg`(=QA, 보호) · `dev`(=통합, 배포 없음). 작업 브랜치는 `feat/…`·`fix/…`·`docs/…`이고 base는 `dev`.

```
feat/x ──PR(squash)──> dev ──PR(merge commit)──> stg ──PR(merge commit)──> main
```

승격 PR을 **merge commit으로 제한**한다. squash하면 승격된 브랜치가 원본과 다른 SHA를 갖게 되어 다음 승격 PR마다 유령 충돌이 난다 — 3브랜치 전략에서 가장 흔한 사고다. `main`에 뭔가 들어가면 즉시 `main`→`stg`→`dev` 역병합한다.

`prd` 브랜치를 새로 만들지 않고 **`main`을 그대로 prd로 쓴다.** GitHub 기본 브랜치·PR base 기본값·기존 보호 규칙·Vercel Production Branch를 모두 그대로 두어 이행 비용이 가장 낮다.

**이것만으로 얻는 것**: 코드가 `stg`에서 한 번 돌아본 뒤 운영에 간다. 브랜치 이름에서 사람이 사라지고 검증 단계가 드러난다. 사소해 보이지만 지금까지는 그 단계 자체가 없었다.

### 2. dev 환경은 배포하지 않는다 (지금 적용)

`dev` 브랜치는 배포 대상이 아니고 각자 로컬에서 돈다. `lib/db/store.ts`의 `getStore()`가 Supabase env가 없으면 `.data/` 파일 스토어로 떨어지므로, **로컬에 Supabase 키를 넣지 않는 것만으로** 완전한 데이터 격리가 된다. 지금 데이터가 격리되는 곳은 여기뿐이다.

### 3. Vercel은 1개 프로젝트 + 환경변수 2스코프 (구조만 적용)

`Production` = prd, `Preview` = stg. 프로젝트를 3개로 늘리는 대신 스코프로 나눈다.

환경마다 달라야 하는 키는 `NEXT_PUBLIC_SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`·`AUTH_SECRET` 3개뿐이고 나머지 공통 키는 한 곳에서 관리된다. 프로젝트를 나누면 공통 키까지 복제되어 **키 로테이션 한 번이 여러 곳을 정확히 맞추는 작업**이 되는데, 2~3인 팀에서 그건 언젠가 반드시 틀린다.

### 4. **Supabase 분리는 보류** (미적용 — 보류 중)

별도 stg 프로젝트를 만들지 않는다. 따라서 **`stg` 배포본은 운영 DB·운영 Storage를 그대로 쓴다.**

이 상태에서 감수하는 것을 그대로 적는다.

| | 얻은 것 | 아직 없는 것 |
|---|---|---|
| 코드 | `stg` 검증 단계 | — |
| 데이터 | 로컬 완전 격리 | **stg에서 만든 계정·리포트·이미지가 실 DB에 쌓인다** |
| 스키마 | — | **마이그레이션을 미리 시험해 볼 곳이 없다** |
| 용량 | — | stg 사용분이 무료 한도(DB 500MB · Storage 1GB)를 같이 먹는다 |

**운용 규칙**: stg에서는 읽기·정상 플로우 확인까지만 한다. 대량 생성·삭제·스키마 실험은 로컬에서.

**해제 조건**: Supabase 프로젝트를 하나 더 만들고 Vercel Preview 스코프에 그 값 3개를 넣으면 끝이다. **코드 변경은 필요 없다** — 지금 구조가 이미 스코프로 갈라져 있다. Free 플랜은 조직당 활성 프로젝트 2개라 한도 안에 들어간다.

### 5. 환경 확진 수단을 코드에 넣는다 (지금 적용)

`supabaseProjectRef()`를 신설해 `/api/report`·`/api/studio/detail`의 GET 진단이 `vercelEnv`와 함께 답하게 했다. 지금은 stg·prd가 **같은 ref를 답하는 것이 정상**이고, DB 분리 후에는 **달라야 정상**이다 — 즉 이 필드가 분리 여부의 판정선이 된다. ref는 공개 URL에 이미 담긴 값이라 노출 위험이 없다.

`scripts/db-push.mjs`는 접속 시도 전에 대상 project ref를 출력한다. Session pooler URI는 호스트에 ref가 안 보여 `.env`를 갈아끼우다 보면 어느 프로젝트를 때리는지 모른 채 실행하게 된다. **DB가 하나인 지금 이 명령은 곧바로 운영 스키마를 바꾸므로** 오히려 더 필요하다.

`db:push:stg` / `db:push:prd` 같은 환경별 스크립트는 **넣지 않았다.** DB가 하나인데 그 이름은 "stg를 때린다"는 거짓 안전감을 준다. 프로젝트가 생기는 시점에 함께 넣는다.

## 기각한 대안

**Vercel 프로젝트 3개(dev/stg/prd).** URL이 깔끔하고 3환경 모두 Instant Rollback을 쓸 수 있다는 이점이 있으나, 환경변수를 3벌로 유지해야 하고 브랜치 push마다 3중 빌드를 막는 Ignored Build Step을 프로젝트마다 걸어야 한다. 신규 프로젝트의 Fluid Compute 설정 누락(→ 함수 60초 → 진단 파이프라인 사망) 위험도 새로 생긴다. **stg에 커스텀 도메인이 필요해지거나 stg 롤백이 필요할 만큼 UT 빈도가 올라가면 재검토한다.**

**Supabase 프로젝트 3개(dev/stg/prd).** 무료 2개 한도를 넘어 별도 조직/계정이나 유료 전환이 필요하고, 7일 무활동 pause를 3개 챙겨야 한다. dev를 로컬로 두면 얻는 격리가 같으므로 비용만 늘어난다.

**단일 Supabase 프로젝트 내 Postgres 스키마 분리(`stg`/`public`).** DB를 안 늘리고 격리하는 유일한 길이라 검토했으나 코드 부채가 크다 — supabase-js `db.schema` 옵션, PostgREST Exposed schemas 설정(누락 시 `PGRST106`으로 전량 거부되는데 런타임에만 드러난다), `schema.sql` 397줄 전체에 search_path 프리앰블(`gen_random_uuid()`가 `extensions` 스키마에 있어 순서가 까다롭다), `scripts/db-push.mjs`의 `table_schema='public'` 하드코딩 파라미터화가 모두 필요하다. **결정타는 Storage 버킷이 Postgres 스키마로 나뉘지 않는다는 것** — 결국 버킷을 따로 만들어야 하므로 프로젝트 분리가 하는 일을 포함하면서 DB 쪽 부채만 얹는다.

**`APP_ENV` 환경변수 도입.** 배포 환경이 둘뿐이라 Vercel이 자동 주입하는 `VERCEL_ENV`(`production`/`preview`)로 충분하다. 관리할 변수를 늘리지 않았다. 배포 환경이 셋 이상으로 늘면 그때 필요해진다.

## 결과

- 브랜치 이름에서 사람이 사라지고 검증 단계가 드러난다. 운영 배포 전에 `stg`가 한 번 낀다.
- **데이터 격리는 아직 로컬에만 있다.** `stg`도 운영 DB를 쓴다는 경고를 [deploy-runbook §2·§9](../deploy-runbook.md)에 그대로 유지한다 — 해소되지 않은 것을 해소된 것처럼 적지 않는다.

## 부수 정정 — 유령 키 `NEXT_PUBLIC_SUPABASE_ANON_KEY`

env 정본 문서 3곳([[../11-deploy-spec]] §4 · [[../09-dev-spec]] §1 · [setup-supabase.md](../setup-supabase.md))이 이 키를 "필수"로 적어 왔으나 **코드가 읽는 곳이 하나도 없다.** `lib/db/supabaseClient.ts`의 `hasSupabaseEnv()`와 `lib/db/store.ts`의 `getStore()` 모두 URL + service_role 2종만 본다. 환경변수 표를 재구성하면서 세 문서에서 제거했다.
