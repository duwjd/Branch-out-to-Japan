# 결정 — 작업 브랜치를 사람 단위로 되돌린다 (2026-08-31)

> [[2026-08-22-환경분리-브랜치전략]] **§1 을 부분 번복**한다. 그 문서의 나머지(환경 축 · dev 미배포 · Vercel 1프로젝트 2스코프 · DB 분리 보류)는 **전부 그대로 유효**하다.

## 배경 — 2인 팀에 기능 브랜치는 무거웠다

2026-08-22 에 작업자 이름 브랜치를 폐지하고 `feat/…`·`fix/…`·`docs/…` 로 바꿨다. 아흐레 써 보니 **기능마다 브랜치를 파고 지우는 비용이 얻는 것보다 컸다.** 2인 팀에서는 "누가 무엇을 만지는지"가 이미 서로 보이고, 브랜치 이름이 그걸 다시 말해 줄 필요가 없다.

## 결정 — 축을 둘로 나눈다

| 축 | 브랜치 | 무엇을 나타내나 |
|---|---|---|
| **환경** | `main` · `stg` · `dev` | **어디까지 검증됐는가** |
| **사람** | `dev-jeongwon` · `dev-hanna` | **누가 지금 만지는가** |

```
dev-jeongwon ──PR(merge)──┐
                          ├──> dev ──PR(merge)──> stg ──PR(merge)──> main
dev-hanna    ──PR(merge)──┘
```

개인 브랜치는 **사람마다 하나이고 병합 후에도 계속 산다.** 기능마다 파지 않는다.

### 왜 2026-08-22 를 번복해도 되는가

그때 사람 이름 브랜치를 없앤 이유는 *"브랜치가 어디까지 검증됐는가를 표현하지 못했다"* 였다. **그 지적은 옳았고, 지금은 해소됐다** — 당시엔 사람 브랜치가 곧장 `main` 으로 갔지만 이제 `dev`→`stg`→`main` 이 그 역할을 한다.

즉 **개인 브랜치는 `dev` 아래의 작업 공간이지 검증 단계가 아니다.** 번복되는 것은 "작업 브랜치를 무엇으로 이름 붙이는가" 하나뿐이고, 그 결정의 본체였던 환경 축은 그대로 선다.

## 동반 변경 — squash 가 사라진다

지금까지는 *"작업 브랜치 → `dev` 만 squash"* 였다. 이건 **병합 후 죽는 브랜치**를 전제한 규칙이다.

`dev-jeongwon` 은 계속 살아서 재사용되므로, squash 하면 `dev` 와 SHA 가 갈리고 다음 back-merge 마다 유령 충돌이 난다 — **2026-08-22 가 승격 PR 에 대해 경고한 것과 정확히 같은 사고**다. 그래서 이제 **저장소의 모든 병합이 merge commit** 이다.

같은 이유로 **`dev-{이름}` 은 rebase 하지 않는다.** push 한 순간부터 공유 브랜치이고, 최신화는 `dev` 를 merge 해서 받는다.

## 감수하는 것

| | 얻은 것 | 대가 |
|---|---|---|
| 운영 | 브랜치를 파고 지우는 단계가 사라진다 | — |
| 리뷰 | — | **PR 이 사람 단위로 묶여 주제가 섞이고 diff 가 커진다.** 리뷰 granularity 가 떨어진다 |
| 이력 | — | **`dev` 이력에 WIP 커밋이 그대로 남는다**(squash 소멸의 대가). Conventional Commits 를 더 지켜야 한다 |
| 충돌 | — | **두 사람이 같은 파일을 만져도 `dev` 에서 만날 때까지 모른다.** back-merge 를 자주 하는 것으로만 완화된다 |

첫 번째 대가는 규칙으로 막을 수 없다. **한 덩어리가 커졌다 싶으면 중간에 `dev` 로 한 번 올리는 것**이 유일한 완화책이고, 그건 사람이 판단한다.

## 영향 없는 것

`.github/workflows/ci.yml` 은 고치지 않았다 — 트리거가 `pull_request: branches: [dev, stg, main]` 이라 `dev-{이름}` → `dev` PR 에서 그대로 돈다. Vercel 설정(Production Branch = `main`, Preview = 나머지)도 그대로다.

## 이행

진행 중이던 `chore/prettier-format`·`chore/prettier-setup`·`ci/verify-workflow` 는 **기존 규칙대로 PR 로 마무리**한다. 이미 origin 에 있는 작업을 새 규칙에 맞추려 옮기면 얻는 것 없이 충돌만 만든다. 새 규칙은 이후 작업부터다.
