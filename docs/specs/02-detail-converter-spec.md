### 관통 원칙 5개

**1. 메시지 재설계 도구다.** 범용 이미지 생성툴이 아니다(금지 포지션 1번과의 경계선). 카피는 번역이 아니라 일본 고객 관점의 재설계이며, 근거 없는 배지·가격·효능 주장은 프롬프트 진입 자체가 불가하다.

**2. 근거가 없으면 그 블록이 없는 페이지가 나오는 것이 정상 동작이다.** 블록 제외는 실패가 아니라 기본값이다. 다만 **왜 빠졌는지**를 항상 사용자에게 말한다(확인 화면 CONFIRM-02).

**3. 문자는 AI가 그리지 않는다.** AI는 글자 없는 배경컷만 만들고, 캐치카피를 포함한 모든 문자는 satori 가 벡터로 렌더한다. 이것이 이 기능의 **구조적 차별점**이다 — 썸네일(콜⑥)에서는 "오탈자 없음"이 프롬프트 부탁이었지만, 여기서는 사실이다.

**4. 산출물의 색은 고객 브랜드의 것이다.** (2026-08-11 신설) 팩의 `moodProfiles` accent 6종이 전부 `#ff6464`(YOAKE 자사 코랄)였고 블록 렌더 토큰도 코랄 고정이었다 — 어느 브랜드로 만들어도 결과물이 같았고, 우리 브랜드색이 고객 상세페이지로 새어 나갔다. 테마는 **생성 산출물에만** 적용되고, YOAKE 앱 화면의 코랄 디자인시스템은 그대로다.

**5. 입력은 한국어로 받고, 출력은 일본어로만 낸다.** (2026-08-11 신설) 사용자는 한국인이다. 일본어 표기를 미리 갖춰 오라고 요구하는 것은 이 서비스가 대신 해야 할 일을 사용자에게 미루는 것이다. 다만 **카피 재설계(콜⑦)와 표기 변환(콜⑧)은 성격이 정반대**다 — 카피는 다시 쓰고, 사실 필드는 값을 그대로 둔 채 표기만 옮긴다. 계약은 §2-9.

> **왜 그렇게 했는가:** 확산 모델의 CJK 글리프 정확도는 문자 수에 대해 곱셈으로 떨어진다. 글자당 99%를 가정해도 20자는 82%, 200자는 사실상 0%다. 썸네일은 카피 2~3줄이라 통했지만 상세페이지는 블록당 200~600자다. 게다가 `※効能評価試験済み` 같은 근거 표기는 **한 글자만 어긋나도 근거로서 무효**가 되고 그게 곧 법적 리스크다.

## 1. 목표 · 비목표

**목표**
1. 제품컷(+한국 상세 원본)을 입력받아, 상세페이지 요소를 **블록 단위 이미지로 만들고 세로로 이어붙인** 완성 이미지를 낸다.
2. 상품 종류에 따라 이미지 분위기가, **프로모션 유무·옵션 개수에 따라 구성이** 달라진다.
3. 법적 가드(景表法·薬機法 인접 영역)가 **구조적으로** 작동한다 — 코드가 게이트를 소유한다.
4. 실제 일본 쇼핑몰에 그대로 올릴 수 있다 — 몰별 규격에 맞춘 **분할본**을 함께 낸다.

**입력 계약** (② DETAIL-02~06d 정본 · 파서: `lib/server/detailForm.ts`)

|---|---|---|---|
| 원본 이미지 1~10장 | **항상 필수** | B03·B24 외 | 첫 장 = 제품 대표컷. 나머지는 KR 상세 원본(위→아래 순서) |

**비목표**
- 범용 상세페이지 빌더. 블록 카탈로그 밖의 자유 레이아웃은 제공하지 않는다.

- HTML 상세(라쿠텐 RMS) 산출 — v1은 이미지만. §6 열린 질문.
- 물리 패키지 현지화.

## 2. 파이프라인 7단계

```
analyze → translate → plan → layout →  copy  → humanize →   blocks   →  compose → slice → gate
 (입력)   (콜⑧ 0~1회) (시퀀스) (톤·높이) (콜⑦ 1회) (콜⑨ 1회)  (AI≤4 + 여백실측  (sharp)  (몰 규격) (검수)
                                                              + satori)
```

`translate` 는 **한글이 하나라도 있을 때만** 실행된다. 일본어로 입력한 사용자에게는 콜이 0회이고 산출도 이 단계 도입 전과 동일하다(§2-9).

`plan`(어떤 블록이 들어가는가)과 `layout`(그 블록이 어떤 톤·높이·배치를 갖는가)은 **둘 다 결정적이고 LLM 미개입**이다. 같은 입력이면 같은 페이지가 나온다.

### ① analyze — 입력 수집
업로드 이미지를 저장하고(순서 = 위→아래), 활성 브랜드·브랜드명·**브랜드킷** 스냅샷을 물질화한다.

### ①b translate — 콜⑧ inputTranslate (**한글이 있을 때만 · 0~1회**)
사용자가 한국어로 쓴 **사실 필드**를 일본 표기로 옮긴다. 계약은 §2-9. 확인 화면이 결과를 보여주고 사용자가 고칠 수 있으며, 확정된 값이 `detail_input` 에 저장된다(원문은 `sourceKo` 에 함께 스냅샷).

### ② plan — 블록 시퀀스 결정 (**LLM 미개입, 결정적**)
`planBlocks(input, platform, templateId, disabledBlocks)`:
1. 템플릿의 `blockSequence` 를 펼친다.
2. 조건부 레이어를 삽입한다 — 프로모·실적은 head, 옵션은 히어로 다음.
2b. **카테고리 샷 보강**(2026-08-18 신설, §2-12): `categoryShotPlan` 의 필수·선호 컷이 시퀀스에 없으면 마무리 구간(사용법·스펙표·각주) **앞에** 끼워 넣는다.
3. **게이트**: 각 블록의 `requires` 토큰을 입력에 대해 평가. 하나라도 미충족이면 **블록째 제거**하고 사유·해결힌트를 기록한다.
4. **AI 상한**: 이미지 생성 블록이 `MAX_AI_BLOCKS(6)` 를 넘으면 **우선순위 순으로** 잘라 hybrid 는 text 로 강등, ai-visual 은 제외(§2-12). 선착순이 아니다.
5. **법적 블록 고정**: `TEXT_ONLY_BLOCKS` 는 팩 값과 무관하게 `renderKind='text'`. 승격 불가.
6. 각주 블록을 항상 마지막으로.

> 같은 입력이면 같은 시퀀스가 나와야 하므로 이 단계에 LLM을 넣지 않는다. 확인 화면(CONFIRM)은 이 함수의 산출을 그대로 보여준다 — 화면이 따로 추론하지 않는다.

### ②b layout — 밴드 톤·높이·배치 결정 (**2026-08-11 신설 · LLM 미개입, 결정적**)
`planLayout(blocks)` — 계약은 §2-6. 블록 단위 순수 함수로는 만들 수 없다(톤 교대가 앞 블록에 의존하는 **접기 연산**). 그래서 확정된 시퀀스 전체를 한 번에 받아 배열을 낸다. 블록 재생성 경로도 같은 함수를 같은 순서에 적용해 일관성을 보장한다.

> **왜 별도 단계인가:** 지금 `BlockRenderContext` 는 `{ brandName, hasBackground }` 뿐이라 블록이 **자기가 몇 번째인지, 앞뒤가 뭔지 모른다.** 구조적으로 리듬을 만들 수 없다. "슬라이드 나열"의 근본 원인이 여기다 — 블록 하나하나의 디자인 문제가 아니라 블록들 사이에 관계가 없는 문제였다.

### ②c humanize — 콜⑨ copyHumanize (**1회 · 실패해도 잡을 죽이지 않는다**)
콜⑦이 채운 일본어 카피의 **문체만** 다듬는다. 계약은 §2-11. `assembleBlockSlots` **이전에** 돌아
코드 소유 값(가격·실적·시험·전성분)에는 아예 닿지 않는다.

### ③ copy — 콜⑦ detailCopy (Claude 비전 1회)

## 2-6. 밴드 리듬 계약 (2026-08-11 신설)

### 밴드 톤 4종

| tone | bg | ink | body | accent(텍스트) | fill(채움) | rule | card |
|---|---|---|---|---|---|---|---|
| `paper` | `#ffffff` | `#202124` | `#414245` | `accentStrong` | `accent` | `#ebebeb` | `#f7f7f8` |
| `tint` | `mixWhite(accent, 0.90)` | `#202124` | `#414245` | `accentStrong` | `accent` | `mixWhite(accent, 0.74)` | `#ffffff` |

> **tint 배경이 `surface`(0.965 혼합)가 아니라 0.90 혼합인 이유:** `surface` 는 **AI 배경컷 프롬프트용 연한 색**이다. 그대로 밴드에 쓰면 흰색과 3.5% 차이라 교대가 눈에 보이지 않는다. 실제로 현행 코드에 tint 블록이 5개 있는데 아무도 알아채지 못했다 — 리듬 장치가 있는데 없는 것처럼 보이던 원인이다.

### 교대 규칙 (`planLayout`)

1. 비주얼 블록(`renderKind !== 'text'`)은 `paper`. 사진이 밴드를 채우므로 이 톤은 **배경컷 생성 실패 시의 폴백 배경**이다.
2. 비주얼 블록에 **인접한** 블록은 `accent`·`ink` 금지. 사진 옆 강한 색면은 사진을 죽인다.
3. `accent`·`ink` 는 페이지당 각 **최대 2회**, 서로 인접 금지.
4. 팩에 `tonePreference` 가 있으면 우선(예: `mall-promo-banner`→accent, `cumulative-sales`→ink, `footnote-block`→paper).
   `color-chip-grid`·`color-chart-matrix` 는 **paper 고정** — 스와치가 사용자 입력 색이라 어두운 밴드 위에서 사라진다.
5. 그 외(`auto`)는 `paper` 2연속 금지로 교대한다.

> ⚠ **초안의 "비주얼 인접은 paper 강제" 는 폐기했다.** tint 교대까지 막아 D3에서 paper 가 **11연속**으로 이어졌다 — 고치려던 문제를 그대로 재생산했다. 금지 대상을 강한 톤으로만 좁힌 뒤 전 템플릿에서 텍스트 블록 기준 paper 연속이 최대 2로 떨어졌다(실측).

## 2-7. 테마 해석 (2026-08-11 신설)

### 우선순위와 폴백

```
custom(직접 입력 hex) → palette(프리셋) → auto(제품컷 추출) → 카테고리 기본 팔레트
```

2단계 저장: **브랜드 관리(BRAND-11)의 `brand_theme`** 가 기본값, **생성 폼(DETAIL-04b)** 이 건별 오버라이드. 생성 시점의 **해석된 값**(hex 4종 + moodKeywords)이 `generated_assets.detail_input.theme` 에 스냅샷된다 — `regenerateBlock` 이 읽는 유일한 입력이라 **신규 컬럼 0개**로 재생성 일관성이 확보된다.

> `products` 테이블까지 3단계로 가지 않는다. 상세페이지 파이프라인은 `ProductRecord` 를 전혀 참조하지 않고 생성 폼에 "제품 선택" 스텝 자체가 없다 — 이득 대비 과하다.

### 색 추출 (`extractAccent`)

```
1. 96×96 로 다운스케일 (canvas drawImage / sharp resize)
2. 픽셀별 RGB → HSV
3. 제외 규칙 — 배경·그림자·하이라이트를 걷어낸다
     S < 0.18                       무채색(흰·회 스튜디오 배경)
     V < 0.12                       그림자
     V > 0.96 && S < 0.30           하이라이트·화이트 배경
4. 남은 픽셀을 hue 24버킷(15°)에 가중 누적
     weight = S × (1 − |V − 0.55| × 0.8)    채도 높고 중간 밝기 = 브랜드색일 확률 높음
5. 최대 버킷 + 좌우 인접 버킷 합산(hue 경계 분산 보정) → median H·S·V → RGB
6. clampFill(1.6)
7. coverage < 3% → 신뢰 불가 → 카테고리 기본 팔레트로 폴백(그 사실을 화면에 밝힌다)
```

**입력은 반드시 `sourceImagePaths[0]`(제품 대표컷)만.** 2번째 장부터는 한국 상세페이지 원본이라 한국어 UI 색(빨강 세일 배너 등)이 섞여 결과를 오염시킨다. 코드로 못박는다.

**무드 추정** — `meanS`·`meanV`·`contrast(p90V−p10V)`·dominant hue 로 판정. 제안일 뿐 사용자가 바꾼다.

```
meanV > 0.82 && meanS < 0.25   → minimal-clean
meanV < 0.45                    → luxury
contrast > 0.62 && meanS > 0.45 → bold-editorial
hue ∈ [150,210] && meanV > 0.7  → fresh
meanS < 0.35 && meanV > 0.7     → pastel
hue ∈ [60,150]                  → natural
else                            → minimal-clean
```

### 파생 토큰 (순서가 중요하다)

```
accent       = clampFill(raw, 1.6)              흰 배경에서 최소 1.6:1 — 안 하면 연한 색이 그래프 바에서 사라진다
accentTint   = mixWhite(accent, 0.94)
surface      = mixWhite(accent, 0.965)          AI 배경컷 프롬프트용 (밴드 배경 아님 — §2-6 참조)
accentStrong = deriveStrong(accent, accentTint, 4.5)
accentBand   = deriveBand(accent, 4.5)
onAccent     = bestOn(accentBand)
```

- `darken()` 은 **sRGB 채널 균등 스케일**이다. HSL 명도 조작과 달리 R:G:B 비율이 유지되므로 HSV 색상·채도가 정확히 보존된다 — 브랜드색의 정체성이 남는다.
- `deriveStrong` 의 기준 배경을 흰색이 아니라 **그 색이 실제로 얹히는 `accentTint`** 로 두는 게 핵심이다. accentTint 가 흰색보다 어두우므로 여기서 4.5를 넘기면 흰 배경 위는 자동으로 더 안전하다. (현행 코드의 실제 결함이 여기서 잡힌다 — `coralStrong #d93636` on `coralTint #fff8f8` = **4.42:1** 로 미달)
- `deriveBand` 는 **중간 밝기 accent 전용 보정**이다. `#8a7f76` 같은 색은 흰 글자도 잉크 글자도 4.5를 못 넘긴다(실측 4.12). 그럴 때만 대비가 유리한 방향으로 밀어 4.5를 확보한다 → `#938980`(4.70). 다른 9개 팔레트는 원색 그대로 통과한다.

### 프리셋

**팔레트 10종** (전부 파생 후 AA 통과 실측 확인)

| id | 라벨 | accent | 영문명(프롬프트용) |
|---|---|---|---|
| `neutral-greige` | 뉴트럴 그레이지 | `#8a7f76` | warm greige |
| `clinical-blue` | 클리니컬 블루 | `#3d6fb5` | deep clinical blue |
| `fresh-aqua` | 프레시 아쿠아 | `#1f9aa6` | fresh aqua teal |
| `botanical-green` | 보태니컬 그린 | `#4f7a52` | botanical green |
| `rose-coral` | 로즈 코랄 | `#e8556e` | soft rose coral |
| `soft-pink` | 소프트 핑크 | `#d4788f` | muted rose pink |
| `warm-beige` | 웜 베이지 | `#b08356` | warm sand beige |
| `lavender` | 라벤더 | `#7d6bb0` | soft lavender |

`#ff6f61`(YOAKE 코랄, 2026-08-18 팔레트 통일 이후의 브랜드 원색)은 **팔레트 목록에 넣지 않는다.** 구 `#ff6464`도 마찬가지다. 고객이 우연히 우리 색을 고르는 것과 우리가 강요하는 것은 다르다 — 필요하면 `rose-coral` 이 그 자리를 대신한다.

**무드 8종** — `minimal-clean` · `clinical` · `natural` · `luxury` · `fresh` · `pastel` · `bold-editorial` · `warm-daily`.
각 무드의 영문 `keywords` 는 카테고리 keywords 를 **대체하지 않고 뒤에 잇는다**. 카테고리 키워드는 상품에 맞는 장면 문법(선케어의 `water droplets, summer air`)이라 브랜드 무드가 지워선 안 된다.

### 프롬프트 주입

`buildBlockPrompt()` 의 `{{moodKeywords}}`·`{{surfaceColor}}`·`{{accentColor}}` 치환값이 `moodProfiles[category]` 대신 해석된 테마에서 온다. 색은 **hex만 주지 않고 영문명과 함께** 넣는다 — `soft rose coral (#e8556e)`. hex만으로는 이미지 모델이 거의 따르지 못한다(썸네일 픽스처가 이미 쓰는 관례).

팩의 `moodProfiles` 에서 `accent` 6종은 **제거한다.** 더 이상 읽히지 않는데 남겨두면 다음 사람이 "여기가 색 정본"이라고 착각한다.

### 코드 이식 시 반드시 지킬 것

- **모듈 전역 `let T` 를 갈아끼우는 방식 금지.** satori 는 `blockContent` 가 반환한 **뒤에** 함수 컴포넌트를 호출하고 `detailJob.ts` 의 블록 렌더는 `Promise.all` 이다 — 동시에 도는 다른 브랜드의 테마로 오염된다. **팩토리 클로저만** 허용한다(React Context 도 불가 — satori 는 리컨실러를 돌리지 않는다).
- `DetailInput.theme`·`brandKit` 은 **optional.** `regenerateBlock` 이 구 자산의 `detail_input` 을 그대로 읽으므로 required 면 기존 자산의 블록 재생성이 죽는다. 접근은 `detailThemeOf()` 액세서 하나로만.
- 폼에서 온 `paletteId` 는 화이트리스트, `customAccent` 는 `normalizeHex()` 통과분만. **여기서 sanitize 하지 않으면 사용자 문자열이 그대로 satori 스타일과 AI 프롬프트에 들어간다.**

## 2-10. 배경컷 여백 실측 · 카피 배치 (2026-08-18 신설)

정본 구현: `lib/studio/detail/safeArea.ts` · 검증: `safeArea.test.ts`(합성 이미지로 판정식 고정).

### 무엇이 문제였나

배경컷 블록의 카피가 **화면 세로 중앙**(`justifyContent:'center'`)에 92% 불투명 흰 카드
(`OverlayCard`)로 얹혔고, 사진 전면에 흰 스크림 0.12 가 깔렸다. 제품은 대체로 화면 가운데 있으므로
**카드가 곧 제품을 덮었다.** 게다가 팩의 `heroPlacement`·`copyZone` 슬롯(좌/우)은 이미지 프롬프트에만
가고 렌더에서 버려져, 모델이 `left` 를 고르면 제품과 카드가 같은 쪽에 겹쳤다.

### 알고리즘

```
1. sharp(buf).resize(64, 96, {fit:'fill'}).greyscale().raw()      6,144바이트 · 수 ms
2. 4열 × 6행 = 24셀. 셀마다 meanLuma(평균 밝기) · busy(이웃 절대차 = 간이 엣지 밀도)
3. 가장자리에 붙는 후보 11종 — 하단/상단 밴드·절반, 좌/우 절반, 네 모서리, 중앙(최후)
     density = mean(busy) + stdev(busy) × 0.6
     score   = density − (셀 수 / 24) × 0.03      ← 넓이 보너스
4. 최저 score 채택. 동점은 배열 순서(하단 → 상단 → 좌우)
5. 글자색 = 구역 밝기. luma < 0.52 → 흰 글자 + 어두운 그라디언트, 그 외 → 잉크 + 밝은 그라디언트
6. 스크림 알파 = 4.5:1 을 넘기는 **최소값**을 이분 탐색(상한 0.92)
7. density > 0.10 이면 = 뚜렷한 여백 없음 → 자리는 그대로 두고 알파를 상한으로, confidence 0,
   사유를 블록 행 error 에 남긴다(조용히 가리지 않는다)
```

**설계 판단 4개**

- **왜 LLM 비전이 아닌가.** 배경컷은 콜⑦ **이후에** 생성되므로 기존 비전 콜을 재사용할 수 없고,
  블록마다 비전 콜을 붙이면 최대 4콜·수십 초가 더 든다. "무엇이 그려졌나"가 아니라 "어디가 비었나"를
  묻는 문제라 픽셀 통계로 충분하고, **결정적이라 블록 재생성 시 배치가 흔들리지 않는다.**
- **미세 질감은 일부러 지운다.** 8배 축소에서 천 결·필름 노이즈는 평균으로 사라진다. 재려는 것은
  구도 규모의 구조물(제품·소품·잎)이다. ⚠ 그래서 테스트 픽스처도 1px 줄무늬가 아니라 32px 격자여야 한다.
- **넓이 보너스가 필요한 이유.** 엇비슷하게 빈 구역이라면 넓은 쪽이 낫다 — 좁은 구역에서는 헤드라인이
  어절 중간에서 꺾이고 글자도 작아진다(`templates.tsx` 의 `widthFit`). 실측 밀도차(0.01~0.05)보다
  작게 잡아 **거의 동점일 때만** 갈리게 한다.
- **대비만으로는 판정할 수 없다.** 알파를 상한까지 올리면 어떤 사진 위에서도 대비는 확보된다.
  "읽히는가"와 "제품을 안 가리는가"는 다른 질문이고, `CALM_SCORE_LIMIT` 이 보는 것은 후자다.

### 팩 쪽 변화 (같은 커밋)

`commonConstraints` 의 `"Keep the composition calm"` 을 **걷어냈다** — 페이지 전체를 밋밋하게 만들던
문구다. 대신 "여백 한 덩어리(30% 이상)만 확보하고 나머지는 확실하게 연출하라"로 바꾸고, 조명 지시를
1줄 더 넣었다. 어디를 비울지는 모델이 구도에 맞게 정하고 **코드가 그것을 찾아간다.**

`heroPlacement`·`copyZone` 은 생성 구도 변주용으로만 남는다 — 렌더 배치가 생성 **결과**를 재서 정하므로
두 값이 렌더와 어긋날 여지가 사라졌다.

⚠ **배경컷이 없으면(`hasBackground=false`) 배치를 `inset` 으로 강제 덮어쓴다.** 이 개정의 최대 실패
모드가 "흰 배경에 흰 글자"다. `renderContext.renderContextOf()` 가 한자리에서 막는다.

## 2-11. 일본어 카피 자연성 — 콜⑨ copyHumanize (2026-08-18 신설)

### 왜 별도 콜인가

`/humanize`(`.claude/skills/humanize-korean/`)는 Agent 툴·`_workspace/` 파일트리·Python 게이트에
의존하는 **Claude Code 저작 시점 하네스**이고 **한국어 전용**이다(70패턴이 조사·이중피동·형식명사 등
한국어 형태론 기반). Next.js 런타임에서 부를 수 없다. 그래서 **원리를 일본어용으로 이식**했다.

- 루브릭: `lib/engine/grounding/index.ts` 의 `JP_NATURALNESS_RUBRIC`. 콜⑦·콜⑨에 함께 실린다.
- 전이시킨 카테고리: D(AI 관용구) · C(구조 패턴) · E(리듬 균일) · A(번역투 — **KR→JP 간섭**으로 재작성)
  · H(접속사) · F(과잉 수식) · I(형식명사).
- ⚠ **G(hedging)는 이식하지 않았다.** 일본 상세페이지는 ※각주·「個人差があります」로 **정당하게**
  완곡하며 그것이 곧 약기법·景表法 대응이다. 여기서 hedging 을 깎으면 기존 법적 가드와 충돌한다.

### 안전 계약

`runStructuredCall` 의 `validate` 에 문체 규칙을 **넣지 않는다** — `client.ts` 는 교정 1회 후 throw 라
모델이 두 번 고집하면 상세페이지 생성 전체가 죽는다(§2-9 안전규칙 4의 선례). 사후 검사 → 채택/폐기 →
게이트 기록으로 처리한다.

**사후 검사 5종. 순서가 곧 사유의 정확도다** — 구조를 먼저 보고 값을 나중에 본다.

| # | 검사 | 실패 시 |
|---|---|---|
| ① | 빈 결과 | 원문 유지 |
| ② | 항목 수(줄) 보존 | 원문 유지 — 슬롯 형식이 깨지면 렌더 트리가 다른 모양이 된다 |
| ③ | `※n` 마커 집합 동일 | 원문 유지 — 고아 각주 = 打消し表示 누락 |
| ④ | 숫자 보존(`digitSignature`) | 원문 유지 — 값이 바뀌면 景表法 리스크 |
| ⑤ | 한글 잔존 · 폰트 커버리지 · 브랜드 금지 표현 | 원문 유지 |

> ⚠ ③을 ④보다 **먼저** 본다. `※1` 이 사라지면 숫자 서명도 함께 달라지는데 그때 "숫자가 바뀌었습니다"
> 라고 말하면 사용자는 가격을 의심한다 — 실제 문제는 각주 누락이다. ④는 마커를 걷어낸 뒤 비교한다.

콜 자체가 실패하면 전부 원문으로 진행한다. 게이트 `jpCopyNaturalness` 는 **비차단 등급**이다
(`brandKitApplied` 와 같은 등급, `passed` 판정 불변).

**부수 효과** — `brandKit.toneGuide`·`forbiddenTerms` 가 콜⑧에는 실리는데 콜⑦에는 안 실리던 갭을
이 콜이 닫는다.

## 2-12. 배경컷 연출 · 카테고리 샷 플랜 (2026-08-18 신설)

### 무엇이 문제였나

직전 개정에서 배치·톤·테마를 고쳤는데도 **사진 자체**가 밋밋하고 카테고리와 무관했다. 원인 셋:

| 증상 | 원인 |
|---|---|
| 컷에 연출이 없다 | 화면에 무엇을 세울지는 LLM 슬롯(`sceneDescription` 등)이 정하는데, 슬롯 설명이 `"배경 연출(영문)"` 3~5글자였다. 콜⑦ grounding 에도 아트디렉션 줄이 하나도 없었다 |
| 카테고리에 안 맞는 컷 | 어떤 사진 블록이 들어가는지가 100% `template.blockSequence` 였다 — 사용컷은 D3에만, 제형컷은 D2·D4에 없었다 |

| 도해가 망가진다 | `dramaProfiles` 와 조명 제약이 **모든** AI 블록에 붙어, `"clean flat vector-style infographic"` 인 비교 도해에 `"Never flat, evenly-lit"` 가 덧씌워졌다 |

| shotType | 블록 | dramaAffinity |
|---|---|---|
| `hero` | hero-product | scene |
| `mood` | problem-hook | scene |
| `usage` | usage-scene | scene |
| `texture` | texture-shot | scene |
| `swatch` | swatch-demo | scene |
| `story` | brand-story | scene |
| `look` | personal-color-look | scene |

`dramaAffinity` 는 연출 지시를 받는 블록인지 가른다. `graphic` 은 `dramaProfiles`·`sceneConstraints`
대신 `graphicConstraints`(평면 벡터·여백·pastel)를 받는다. 같은 샷타입을 두 블록이 갖지 못한다(팩 무결성 테스트).

> `soft even light` 가 같은 프롬프트 안의 `"Avoid flat, evenly-lit catalogue lighting"` 과 충돌해
> 결과가 밋밋한 쪽으로 무너졌다. 조명은 한 층만 소유한다(`theme.test.ts` 가 회귀를 막는다).

### 이미지 예산 배분 — 선착순이 아니다

`imagePriority(blockId, category, templateId)` 가 단독 소유한다. 작을수록 먼저 받고, 동점은 시퀀스 순서로 깬다(결정성).

| 우선 | 대상 |
|---|---|
| 0 | `hero-product` — 어떤 경우에도 포기하지 않는다 |
| 1 | 카테고리 `must` 샷 |
| 2 | 템플릿 `signatureBlocks` |
| 3 | 카테고리 `prefer` 샷 |
| 4 | 나머지 |

`MAX_AI_BLOCKS` 4 → **6**, `IMAGE_CONCURRENCY` 4 → **6**. 두 값은 **같이 움직인다** — 소요를 정하는 건
장수가 아니라 웨이브 수이고, 6장을 한 웨이브(실측 40~90초)로 끝내는 게 목적이다.
캡 6에서 최악 조합(D3/D1 + 색상옵션 + 모델컷 동의)이 5~6장이라 실제로 밀려나는 블록은 없다 —
이 우선순위는 병리 케이스 안전망이자 아래 마감 가드의 강등 순서다.

### 마감 예산 가드 (`budget.ts`)

`maxDuration = 300` 은 **Vercel Hobby 플랫폼 상한**이라 올릴 수 없다(11 §2). 시간을 사는 대신
가진 예산을 결정적으로 쓴다. 이미지 웨이브 **직전에** `fitImageBudget(candidates, remaining, concurrency, timeout)`.

```
JOB_BUDGET_MS      270_000   // 300초 − 결합·분할·게이트·저장 30초
COMPOSE_RESERVE_MS  30_000
IMAGE_WAVE_MS       90_000   // 실측 40~90초의 상단(비관값)
```

- **웨이브 단위로만 자른다.** 한 웨이브 안의 장수를 줄여 봐야 동시에 도니까 시간이 줄지 않는다 —
  6장을 5장으로 줄이는 건 사진 한 장을 공짜로 버리는 짓이다.
- 한 웨이브조차 예산을 넘으면 장수가 아니라 **1콜 상한**을 조인다(하한 30초 — 그 아래는 정상 호출까지 자른다).
- 히어로는 예산이 0이어도 남긴다. 제품이 한 번도 안 서는 상세페이지는 실패한 페이지다.
- 잘린 블록은 기존 `degraded` 경로를 그대로 타 한국어 사유가 화면에 뜬다(신규 UI 0).
  `ai-visual` 은 배경 없이 남길 게 없어 `failed` 로 기록하고 사용자가 그 블록만 다시 만든다.

> 왜 필요한가: 그냥 진행하면 함수가 300초에서 죽고 **모든 블록이** 스테일 가드로 실패한다 —
> 사진 몇 장을 포기하는 것보다 훨씬 나쁜 결과다.

### 콜⑦의 두 번째 축 — 연출 브리프

`DETAIL_ART_DIRECTION`(grounding). 카피 루브릭과 **섞지 않고 따로 세운다** — 산출물이 일본어 문장이
아니라 **영문 촬영 브리프**이고, 그 문자열이 그대로 이미지 모델의 프롬프트가 되기 때문이다.
페이로드에는 이 시퀀스에 실제로 들어간 컷의 `shotGrammar` 만 싣는다(없는 컷의 문법까지 보내면
모델이 그 장면을 다른 슬롯에 흘린다).

목 픽스처의 연출 슬롯도 **같은 `shotGrammar` 를 읽는다**(`fixtures.ts`). 하드코딩하면 목과 실경로가
다른 연출을 보게 되고, 그러면 `detail:cli`·`detail:previews` 로 아무리 눈으로 봐도 실제 품질을 알 수 없다.

## 2-13. 시간 예산 · 강등 규칙 (2026-09-02 신설)

이 절은 새 설계가 아니다. `lib/studio/detail/budget.ts` 가 이미 하고 있는 일을 **계약으로 올리고**, 아직 비어 있는 자리를 표시한다.

### 왜 예산이 필요한가

`maxDuration = 300` 은 Vercel Hobby(Fluid Compute)의 **플랫폼 상한**이라 올릴 수 없다(11 §2). 잡을 더 빠르게 만들 수도, 시간을 더 살 수도 없다. 그래서 **가진 예산을 결정적으로 쓴다.**

| 상수 | 값 | 근거 |
|---|---|---|
| `JOB_BUDGET_MS` | 270초 | 300초에서 30초를 뗀다. 마감을 재는 시점이 함수 시작과 다르기 때문이다 — 폼 파싱·이미지 저장·readiness 점검·응답 반환이 이미 끝난 뒤에 잡히므로 우리 시계 270초는 함수 시계로 약 281초다 |
| `COMPOSE_RESERVE_MS` | 30초 | 이미지 웨이브 뒤에 반드시 남겨야 하는 몫. satori 15블록 + sharp 결합·분할 + 게이트 + 저장이 여기서 산다 |
| `IMAGE_WAVE_MS` | 90초 | 이미지 1장의 기대 소요. 실측 40~90초의 **상단**이다. 낙관값을 쓰면 가드가 늦게 걸려 존재 이유가 사라진다 |

`JOB_BUDGET_MS` 는 ① 진단 리포트의 `REPORT_BUDGET_MS` 와 **같은 값·같은 규칙**이다(`lib/engine/reportBudget.ts`). 두 축이 서로 다른 숫자를 쓰면 런북이 두 벌이 된다.

**상수는 확정이 아니라 실측 갱신 대상이다.** 모델·effort·이미지 캡을 바꾸면 여기부터 다시 잰다.

### 강등 규칙 — 통째로 실패하지 않는다

시간이 모자라면 **품질을 낮춰서라도 발행한다.** 통째로 `failed` 가 가장 나쁜 결과다. 사진 몇 장을 포기하는 것과 모든 블록을 잃는 것은 비교 대상이 아니다.

강등은 이미지 웨이브 **진입 직전**에 한 번 판정한다. 이미 시작한 콜을 중간에 끊지 X.

| 순서 | 무엇을 한다 | 왜 |
|---|---|---|
| 1 | 남은 시간에서 `COMPOSE_RESERVE_MS` 를 뺀 값이 가용 시간이다 | 결합·분할 몫은 어떤 이미지 콜도 침범할 수 X |
| 2 | 가용 시간 ÷ `IMAGE_WAVE_MS` 로 감당할 **웨이브 수**를 구한다 | |
| 3 | 우선순위 낮은 컷부터 **웨이브 단위로** 자른다 | 한 웨이브 안의 장수를 줄여도 동시에 도니까 시간이 줄지 X — 6장을 5장으로 줄이는 건 사진 한 장을 공짜로 버리는 짓이다 |
| 4 | 한 웨이브조차 예산을 넘으면 장수가 아니라 **1콜 상한**을 줄인다 | 하한 30초. 이보다 짧으면 정상 호출(40~90초)까지 잘라 가드가 오히려 실패를 만든다 |
| 5 | 잘린 블록은 배경컷 없이 **텍스트로 렌더**하고 사유를 붙인다 | 블록이 사라지는 것이 아니라 사진만 빠진다 |

우선순위는 `blockPack.imagePriority()` 가 **단독으로 소유**한다. 예산 코드에서 규칙을 다시 쓰지 X.

### 히어로는 어떤 경우에도 남긴다

`priority 0`(히어로)은 예산이 아무리 모자라도 자르지 X. 제품이 한 번도 서지 않은 상세페이지는 실패한 페이지이고, 그럴 바에는 시간을 넘겨 재시도를 받는 편이 낫다. 이것은 최적화가 아니라 **불변식**이다.

### 사용자에게 보이는 것

강등이 걸린 블록에는 이 문구가 그대로 화면에 노출된다. **이 문장이 정본이다.**

> 남은 생성 시간이 부족해 이 블록은 배경컷 없이 만들었습니다. 결과 화면에서 이 블록만 다시 만들 수 있습니다.

- 강등은 **실패로 표시하지 X.** 자산 상태는 `done` 이고 블록 상태도 `done` 이다
- 사용자가 할 수 있는 일(블록 단위 재생성)을 같은 문장에서 말한다
- 배포 운영 관점에서도 **정상 동작**이다(11 §7) — 반복되면 앞단 콜 소요를 먼저 본다

### 아직 비어 있는 자리 — 콜 단위 상한

**전체 예산만 있고 앞단 LLM 콜에는 상한이 없다.**

| | ① 진단 리포트 | ② 상세페이지 |
|---|---|---|
| 잡 전체 예산 | `REPORT_BUDGET_MS` | `JOB_BUDGET_MS` |
| 이미지 1콜 상한 | 해당 없음 | `fitImageBudget.perImageTimeoutMs` |
| **LLM 콜 단계별 상한** | `callTimeout(stage, remaining)` | **없음** |

SDK 기본 타임아웃은 10분이라 **함수 상한 300초보다 길다.** 콜 하나가 매달리면 그 콜이 함수를 통째로 먹고, 이미지 웨이브는 시작조차 못 한다. 리포트를 20/20 죽였던 원인이 이것이다(폴백 부재가 아니었다).

대상은 콜⑧ `inputTranslate` · 콜⑦ `detailCopy` · 콜⑨ `copyHumanize` 셋이다. 셋 다 `runStructuredCall` 을 타므로 `StructuredCallOptions.timeoutMs` 가 이미 받는다 — 넘겨주기만 하면 된다.

**이 상한은 스케줄이 아니라 폭주 차단선이다.** 단계 상한을 "다음 단계들이 쓸 시간을 뺀 값"으로 잡으면 정상 소요까지 잘라 가드가 실패를 만든다. 상한은 **실측 최악값에 여유를 얹은 값**으로 두고, 거기에 "결합·분할 몫은 어떤 콜도 먹지 못한다"는 하드캡만 겹친다. 정상 실행은 이 가드를 스치지도 X.

### 계기가 남겨야 하는 것

**상수를 다시 잡으려면 실측이 먼저다.** UT 는 20/20 성공했고(중앙 171초 · 115~210) 지금 나는 실패는 그 이후 조건이라, 재현 데이터 없이 상수를 만지지 X.

기록 위치는 신규 컬럼이 아니라 `detail_input` jsonb 안이다(`theme`·`humanizeIssues` 선례). 새 필드는 전부 optional 로 둔다 — 블록 재생성이 **구 자산의 `detail_input` 을 그대로** 읽으므로 required 로 두면 기존 자산의 재생성이 죽는다.

| 남길 것 | 왜 |
|---|---|
| stage 별 소요(`analyze`→`plan`→`copy`→`blocks`→`compose`→`slice`→`gate`) | 어느 단계가 예산을 먹었는지 자산 레코드만 보고 말할 수 있어야 한다 |
| **실패 경로의 소요** | 안 남기면 정작 알고 싶은 케이스가 안 남는다. `failed` 로 확정하기 **직전에** 쓴다 |
| `fitImageBudget` 의 `keep`·`drop`·`waves` | 강등이 실제로 몇 번 걸렸는지 |
| 재시도 횟수 · 강등 건수 | UT 에서 재시도 12건이 시간을 먹었다 |

`detail_input` 은 이미 무겁다(`sourceKo` 18슬롯 + `brandKit`). 기록은 작게 두고, 목록 타입 `GeneratedAssetSummary` 에는 넣지 X.

## 2-9. 입력 언어 정책 · KR→JA 변환 계약 (2026-08-11 신설)

### 무엇이 문제였나

`assembleBlockSlots` 는 사용자 입력 **18슬롯**을 원문 그대로 슬롯에 넣고, satori 가 자단위로 그린다. 그런데 JP 폰트에 한글 글리프가 없어서, 한국어가 들어오면 글자가 깨지는 게 아니라 `safeText()` 가 던지고 **그 블록이 통째로 사라진다**(`status:'failed'` → 결합 제외). `hero-product` 면 필수 블록이 증발한다.

폼 라벨은 전부 한국어인데 placeholder 만 일본어 예시이고, `cautions` · `reviews` · `test.condition/institution/date` · `sales.period` · `promo.gift/footnote/qualifierChips` 는 **placeholder 조차 없어** 한국어 입력을 사실상 유도했다.

한편 이미지 프롬프트는 100% 영어이고 negative 1순위가 "이미지 안에 글자 금지"다 — 제품명·성분은 gpt-image-2 로 **가지 않는다**. 한국어가 이미지 모델에 닿는 경로는 「추가 요청」(`note`)이 `Additional art direction:` 으로 붙는 것 **하나뿐**이었다.

### 대상 필드 (정본은 `translate.ts` 의 `SCALARS`/`LISTS`/`ROWS`)

| kind | 필드 | 취급 |
|---|---|---|
| `regulated` | `spec.category`(区分) · `spec.fullIngredients`(全成分) | 확인 화면에서 **기본 펼침 + 표시 의무 경고**. 区分은 LLM 이전에 결정적 매핑 |
| `numeric` | `spec.volume` · `proof.*` · `sales.*` · `test.condition/date/sampleSize` · `promo.setTitle/gift/footnote/qualifierChips[]` · `specs[].value` · `reviews[].age` | 숫자 보존 검사 필수 |
| `free` | `spec.manufacturer/origin` · `ingredients[].name/purpose` · `freeOf[]` · `specs[].label` · `howToSteps[]` · `options[].name` · `cautions[]` · `reviews[].text` · `test.name/institution` | 일본 관례어로 |
| `artDirection` | `note` | **일본어가 아니라 영어**. 프롬프트 나머지가 전부 영어라 언어를 섞으면 지시가 흐려진다 |

> ⚠ 새 입력 필드를 추가할 때 `translate.ts` 의 선언에 등록하지 않으면, 한국어로 입력됐을 때 **그 블록만 조용히 사라진다.**

### 처리 순서

```
collectTranslatable   한글이 섞인 필드만 수집 → 0개면 콜 없음(비용·지연 0)
      ↓
preTranslate          결정적으로 끝낼 수 있는 것 먼저
                       1) 区分 매핑표(화장품→化粧品 · 의약외품→医薬部外品 …)
                       2) brandKit.productNamesJa 사전 치환(긴 표기 우선)
      ↓
콜⑧ inputTranslate    남은 것만. 사전·금지표현·톤 가이드를 페이로드에 함께 싣는다
      ↓
사전 후치환            모델 산출에 사전을 한 번 더 적용(한글을 줄이는 쪽으로만 작용)
      ↓
verifyTranslation     사후 검사 3종 — 실패분은 **채택하지 않고 원문을 남긴다**
      ↓
확인 화면              원문 ⇄ 변환 병기, 사용자가 직접 수정
      ↓
applyTranslations     경로 기준 되쓰기 + sourceKo 원문 스냅샷
```

### 안전 규칙

1. **숫자는 값이 바뀌지 않는다.** `digitSignature()` — 천단위 쉼표 제거 → 숫자 런 추출 → 앞자리 0 제거 후 이어 붙여 대조한다. 표기 형식 변화(`2026.04.15` → `2026年4月15日`, `2022.5/19-2026.4/29` → `2022年5月19日〜2026年4月29日`)는 통과하고, 값이 한 자리라도 달라지면 즉시 걸린다. 가격·수량이 조용히 바뀌는 것은 景表法 리스크다.
2. **한글 잔존 0.** 완성형만 보면 안 된다 — 자모 단독(ㄱ·ㅏ)은 JP 폰트 cmap 에 **들어 있어서** `uncoveredGlyphs()` 를 통과한다.
3. **실패는 조용히 넘어가지 않는다.** 검사에 걸린 필드는 원문이 남고, 확인 화면이 사유를 그대로 보여주며, 게이트(`inputTranslated`)에 실패 건수가 기록된다.
4. **금지 표현 검사를 `runStructuredCall` 의 `validate` 에 넣지 않는다.** `client.ts` 는 교정 1회 후 throw 라, 모델이 두 번 고집하면 필드 하나 때문에 콜 전체가 죽는다. 사후 수집 → 게이트 기록(`degradedBlocks` 와 같은 등급, `passed` 판정 불변).
5. **区分은 LLM 에게 맡기지 않는다.** `assembleBlockSlots` 가 `input.spec.category === '医薬部外品'` 문자열 비교로 히어로 블록의 기능 라벨을 켜므로, 표기가 한 글자만 달라도 라벨이 조용히 사라진다. `기능성화장품` 은 `化粧品` 으로 접는다 — 일본 医薬部外品 은 일본 후생노동성 승인 사항이라 한국의 기능성 인정으로 추정할 수 없다(승인 없이 붙이면 허위 표시).
6. **`kr` 대조로 캐시를 검증한다.** 확인 화면에서 블록을 껐다 켜면 plan 라우트가 다시 불리는데, 그 사이 사용자가 입력을 바꿨다면 캐시된 `ja` 는 **다른 값의 번역**이다. 숫자가 없는 필드라면 검사를 전부 통과해 엉뚱한 일본어가 들어간다 — 그래서 원문이 한 글자라도 다르면 캐시를 버리고 다시 부른다.

### 스냅샷 (신규 컬럼 0개 — 전부 `detail_input` jsonb)

| 키 | 내용 |
|---|---|
| `sourceKo` | 변환 전 한국어 원문(감사·되돌리기). 본 필드에는 일본어가 들어가 있다 |
| `artDirectionEn` | 「추가 요청」의 영어 변환. **한국어 원문은 `promptUsed` 가 보관**한다(화면이 사용자 입력을 되비추는 자리) |
| `brandKit` | 생성 시점의 브랜드킷. 브랜드 프로필을 나중에 바꿔도 블록 재생성이 흔들리지 않는다 |
| `translationIssues` | 변환에 실패해 한국어가 남은 필드(게이트 기록용) |

전부 **optional** 이다. `regenerateBlock` 이 구 자산의 `detail_input` 을 그대로 읽으므로 required 로 두면 이 기능 이전 자산의 블록 재생성이 죽는다.

### 목 모드 계약

`fixtures.ts` 의 데모 사전은 **일부러 다 덮지 않는다.** 사전에 없는 표현은 한글이 남은 채 돌아가고 사후 검사가 `ok:false` 로 잡아 확인 패널에 「직접 일본어로 입력해 주세요」가 뜬다 — 즉 목 모드에서도 **실패 경로가 그대로 재현된다.** 전부 성공하는 목은 실패 UX 를 못 만든다.

## 6. 열린 질문

- **Q1. HTML 상세(라쿠텐 RMS) 산출을 지원할 것인가.** 이미지만으로는 SEO·접근성이 약하다. 블록 구조가 이미 있어 HTML 출력은 어렵지 않으나, 몰별 허용 태그가 다르다.
- **Q2. 전성분 원문 확보 경로.** 현재는 사용자 직접 입력이다. ① 리포트 입력에서 재사용하거나 브랜드 자산으로 승격할 수 있다.
- **Q3. 블록 순서 재정렬(생성 후).** v1은 확인 화면에서 on/off만 지원한다. 생성 후 드래그 재정렬은 `asset_blocks.seq` 갱신 + recompose 로 가능하나 UI 비용이 있다.
- **Q4. 비용 모델.** 건당 약 $0.42(이미지 4콜 $0.25 + Claude $0.17). 텍스트 블록 재생성은 $0. `OPENAI_IMAGE_QUALITY=low` 로 이미지 비용을 1/4로 낮출 수 있다.
- **Q5. 제품 패키지 인쇄 문자는 여전히 AI 손에 있다.** 2026-08-11 원본 대조 결과 `images.edit` 는 라벨을 **정확히 보존**했다 — 원본 `rakuten_tvert_352.jpg` 의 `TOUT VERT / BALANCING GA / LOTION`, 하단 영문 4행, `100mL 3.5fl.oz.` 가 히어로·텍스처 두 블록에서 자단위로 재현됐다(2블록/1제품 표본). 8/10에 기록했던 `BALANCING GEL LOTION` → `GA` 변형은 **원본 대조 없이 단정한 오기**로, 원본이 처음부터 `GA`였다. 다만 라벨이 생성 대상인 구조 자체는 그대로이므로 표본을 넓히기 전까지 검수 게이트 문구는 유지한다. 근본 해법(배경만 생성 + 원본 제품컷 sharp 합성, 누끼·배치 로직 필요)은 라벨 열화가 실제로 관측될 때 착수한다.
- **Q7. 추출 색이 제품 패키지색과 브랜드 CI색이 다를 때 무엇을 따르는가.** 지금은 패키지색을 뽑는다(그 제품의 상세페이지이므로). 브랜드 CI를 따라야 하는 케이스가 나오면 BRAND-11에 저장해 두면 그 값이 이긴다 — 우선순위는 이미 그렇게 설계돼 있으나, 사용자가 그 사실을 아는지는 UT에서 확인한다.
- **Q8. 무드 자동 추정의 허용 오차.** 밝기·채도·대비 임계값 6개로 8종을 가르는 휴리스틱이다. 틀려도 사용자가 칩 하나로 바꿀 수 있어 치명적이지 않지만, 첫인상을 좌우하므로 UT에서 "제안된 무드가 맞았는가"를 묻는다.
- **Q11. 여백 실측의 한계는 어디인가.** `safeArea` 는 엣지 밀도·밝기 통계로 판단한다 — 학습 기반 saliency 나 피사체 bbox 가 아니다. 배경 자체가 화려한 컷(패턴 벽지·강한 그라디언트)에서 "비었지만 시끄러운" 구역을 고를 여지가 있다. `confidence` 가 0 인 건수를 UT 에서 세어 보고, 통계로 못 잡는 케이스가 실제로 관측되면 그때 모델을 얹는다.
- **Q9. 슬라이드형 렌더러를 남길 것인가.** 프로토의 대조 토글은 **검토용**이다. 합의되면 밴드 리듬만 남기고 제품에는 토글을 넣지 않는다. 다만 밴드 리듬이 어울리지 않는 몰(아마존 A+ 모듈)이 나오면 프로파일 단위 선택지로 되살릴 여지는 있다.
- **Q10. 全成分 표기 정본을 어디서 얻는가.** 콜⑧이 옮긴 성분명은 **일본 화장품 성분 표시명칭의 정본이 아니다.** 실측 확인(2026-08-11): `정제수, 부틸렌글라이콜, 글리세린` → `精製水、ブチレングリコール、グリセリン` 으로 나왔는데, 일본 상세페이지 관례 표기는 보통 `水、BG、グリセリン` 이다. 둘 다 통용되지만 **정본은 粧工連 표시명칭 리스트**이고 우리는 그것을 갖고 있지 않다. 그래서 (a) 확인 화면에서 기본 펼침 + 표시 의무 경고 (b) 검수 게이트에 "업로드 전 실제 표기와 대조" 기록 (c) 폼에서 일본어 전성분을 그대로 붙여넣도록 권장 — 세 겹으로 사람에게 넘긴다. 표시명칭 사전을 데이터로 확보하면 `brandKit` 용어집과 같은 자리에서 결정적으로 치환할 수 있다.
- **Q6. Storage 정리.** 건당 블록 10~15 + 슬라이스 12 + 마스터 1 = 약 25파일. 브랜드 삭제 시 DB만 cascade되고 Storage는 남는다.
