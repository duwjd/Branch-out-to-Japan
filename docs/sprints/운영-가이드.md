# 스프린트 운영 가이드

> **스프린트를 실제로 굴리는 법.** 무엇을 정했는지는 [[README]], 이번 스프린트 내용은 [[2026-09-phase1]] 에 있다. 여기는 **손이 어디로 가야 하는가**만 다룬다.

## 0. 헷갈리면 이 표로 돌아온다

정본이 셋이고, 각자 담당이 다르다. **같은 내용을 두 곳에 쓰지 않는다.**

| 무엇 | 정본 | 왜 |
|---|---|---|
| 일감의 **지금 상태** | **GitHub Issues** | 알림·PR 연결·권한이 전부 거기 있다 |
| **계획과 회고** | [[2026-09-phase1]] | 왜 이 순서인지, 무엇이 막혔는지는 이슈 제목에 안 들어간다 |
| 보드·칸반·스탠드업 | `.sprint/` (캐시·생성물) | 매번 다시 만들어진다. **커밋하지 않고, 편집하지 않는다** |

한 줄 규칙: **상태는 GitHub 쪽을 바꾸고, 문서는 도구로 맞춘다.** 반대로 하지 않는다.

## 1. 하루 리듬

```bash
npm run sprint:sync        # 아침에 한 번 — GitHub → 캐시
npm run sprint:standup     # 어제 / 오늘 / 블로커
```

작업하고, 상태가 바뀌면 §2 대로 이슈를 고친다. 그리고 하루를 닫을 때:

```bash
npm run sprint:doc-sync            # 문서와 이슈가 어긋났는지 본다
npm run sprint:doc-sync -- --write # 어긋났으면 문서 상태 열을 맞춘다
```

마지막으로 [[2026-09-phase1]] §일자별 기록에 **1~3줄**. 이건 도구가 못 쓴다 — 무엇을 했는지가 아니라 **무엇을 알게 됐는지**를 적는 자리다.

> `sync` 를 건너뛰면 보드가 어제 것이다. 캐시가 12시간 넘으면 세션 시작 때 Claude 가 알려준다.

## 2. 상태 바꾸기

문서의 이모지 4종은 GitHub 상태와 1:1 이다. **이슈를 바꾸면 문서는 도구가 따라온다.**

| 상황 | GitHub 에 하는 일 | 문서 |
|---|---|---|
| 착수했다 | `gh issue edit <번호> --add-label 진행` | ⬜ → 🔵 |
| 남에게/밖에 막혔다 | `gh issue edit <번호> --add-label blocked` | → ⛔ |
| 막힌 게 풀렸다 | `gh issue edit <번호> --remove-label blocked` | → ⬜ 또는 🔵 |
| 끝났다 | `gh issue close <번호>` | → ✅ |

그다음 항상:

```bash
npm run sprint:sync
npm run sprint:doc-sync -- --write
```

**완료는 라벨이 아니라 이슈를 닫는 것이다.** `진행` 라벨은 닫을 때 떼지 않아도 된다 — 닫힌 이슈는 무조건 ✅ 로 읽는다.

### `--write` 가 건드리는 범위

§작업 보드 표의 **상태 열(2번째)만** 바꾼다. 이슈 열이 `—` 인 행(커밋으로 끝난 것)은 건너뛴다. 목표·기간·리스크·§사용자 작업·일자별 기록·회고는 **손대지 않는다.** 표 구조를 못 찾으면 아무것도 쓰지 않고 실패한다.

그래도 정본 문서를 스크립트가 쓰는 것이니, 습관적으로:

```bash
git diff docs/sprints/2026-09-phase1.md
```

## 3. 일감 추가하기

**마일스톤을 통째로 쪼개는 거라면** `/sprint-groom M16` 을 쓴다 — 스프린트 문서·로드맵·dev-spec 을 읽고 이슈 3~7건의 제목·수용 기준·선후관계와 `gh issue create` 명령까지 만들어 준다. **생성은 하지 않는다.** 초안을 보고 사람이 실행한다.

한 건만 추가할 때는 이슈를 먼저 만들고, 문서 표에 한 줄을 잇는다.

```bash
gh issue create \
  --title "M14-5 프리필 실패 시 빈 폼 폴백" \
  --label "M14"
```

라벨 규칙 — 마일스톤 `M13`·`M14`·`M15` 중 하나는 **반드시**. 성격은 선택(`기획` = 구현 선행 기획서, `사용자작업` = 사람만 할 수 있는 일).

그다음 [[2026-09-phase1]] §작업 보드의 해당 마일스톤 표에 행을 추가한다:

```markdown
| 14-5 프리필 실패 시 빈 폼 폴백 | ⬜ | | [#70](https://github.com/duwjd/Branch-out-to-Japan/issues/70) |
```

빠뜨리면 `doc-sync` 가 **"문서 §작업 보드에 없는 열린 이슈"** 로 잡아준다. 지도에 없는 일감은 잊힌다.

> 이슈 없이 커밋으로 끝나는 작은 일도 있다. 그럴 땐 이슈 열에 `— (커밋SHA)` 를 적는다. 도구가 건너뛴다.

## 4. 커밋을 이슈에 잇기

**커밋 본문에 `#번호`를 쓴다.** 제목에 티켓 접두어를 붙이지 않는다 — 이 저장소는 `feat:`·`fix(auth):` 형태이고 기능별 브랜치도 없다.

```
fix(detail): 콜⑦⑧⑨에 개별 타임아웃을 건다

전체 예산만 있고 콜별 상한이 없어 하나가 늦으면 뒤가 다 밀렸다(#58).
```

이러면 스탠드업 "어제" 가 그 커밋을 #58 아래로 묶는다. GitHub 도 이슈에 커밋을 자동 연결한다.

> **`#56~#67` 같은 범위 표기는 잇지 않는다** — "이슈 12건(#56~#67) 생성" 이 12개 작업으로 잡히면 안 되므로 도구가 일부러 걸러낸다.

## 5. Claude Code 안에서

세션을 열면 보드가 **자동으로** 컨텍스트에 들어간다([`sprint-session-start.mjs`](../../.claude/hooks/sprint-session-start.mjs)). "지금 뭐 하던 중이었지"를 다시 설명하지 않아도 된다.

| 명령 | 무엇 |
|---|---|
| `/sprint-sync` | 캐시 갱신 |
| `/sprint-board` | 보드 + 문서 대조 + 병목 지적 |
| `/sprint-standup` | 어제/오늘/블로커를 문장으로 |
| `/sprint-kanban` | 칸반 생성 후 브라우저로 |
| `/sprint-groom <마일스톤>` | 마일스톤을 이슈 3~7건으로 분해 (§3 참고) |

`/status` 와 헷갈리지 않는다 — **`/status` 는 [[../04-roadmap]] 기준 Phase 진척**, `/sprint-board` 는 **이번 2주의 일감**이다.

조회 명령은 승인 없이 돈다. **`gh issue edit`·`close` 는 일부러 허용 목록에서 뺐다** — 상태 변경은 승인 프롬프트가 한 번 막아주는 게 맞다.

### 에이전트는 쓰지 않는다

스프린트 운영에 전용 에이전트를 두지 않기로 했다. 이유는 셋이다.

1. 운영은 **판단이 아니라 계산**이다 — 보드·스탠드업·대조는 스크립트가 답을 확정한다
2. 서브에이전트는 격리 컨텍스트라 **세션 시작 훅의 주입을 못 받는다.** 메인 세션이 공짜로 아는 것을 다시 조회하게 된다
3. 분해·회고는 판단이 필요하지만, 그 판단에 필요한 맥락(열린 이슈·문서 상태)을 **메인 세션이 이미 갖고 있다**

마일스톤이 아직 흐릿해 PRD 부터 필요하면 `/spec`(pm-planner), 여러 역할에 걸친 큰 작업이면 `lead-orchestrator` 를 쓴다. 그건 스프린트 운영이 아니라 기획·조율이다.

## 6. 매일 아침 자동 스탠드업

평일 **09:13 KST** 에 [스탠드업 워크플로](../../.github/workflows/standup.yml)가 [#69](https://github.com/duwjd/Branch-out-to-Japan/issues/69) 에 코멘트를 단다. 코멘트가 곧 알림이라 따로 볼 곳이 없다.

**알아야 할 것 셋.**

1. **`main` 에 있어야 발화한다.** `schedule` 은 default branch 에서만 돈다. `dev-jeongwon` 에만 있으면 아무 일도 안 일어난다.
2. 라벨 `스탠드업` 이 붙은 **열린 이슈 중 가장 최근 것**을 찾아간다. 번호를 하드코딩하지 않았으니 스프린트가 바뀌면 이슈만 새로 열면 된다.
3. Actions 스케줄은 부하에 따라 **수십 분 늦거나 건너뛸 수 있고**, 저장소가 60일 무활동이면 비활성화된다.

수동으로 한 번 돌려보려면:

```bash
gh workflow run "스프린트 스탠드업"
```

## 7. 새 스프린트 시작하기

1. 지난 스프린트 문서의 §회고를 **먼저 쓴다.** 다음 범위의 입력값이다
2. 새 문서 `docs/sprints/YYYY-MM-{phase}.md` — 파일명 규칙을 지켜야 도구가 "현재 스프린트"로 인식한다
3. [[README]] §문서 표에 한 줄 등재 (안 하면 `docs:check` 가 고아 문서로 잡는다)
4. 새 마일스톤 라벨 생성 — `gh label create "M16" --color "0e8a16" --description "..."`
5. 스탠드업 이슈를 새로 열고 라벨 `스탠드업` 을 붙인 뒤, 지난 것을 닫는다

> 지난 스프린트 문서는 **지우지도 옮기지도 않는다.** 파일명이 시간순이라 도구는 마지막 것만 본다.

## 8. 막혔을 때

| 증상 | 원인 · 대응 |
|---|---|
| `캐시가 없습니다` | `npm run sprint:sync` |
| `gh CLI 가 없습니다` / 인증 실패 | `! gh auth login` (대화형이라 사람이 실행). **캐시는 지워지지 않는다** |
| 보드가 실제와 다르다 | 캐시가 오래된 것이다. `sync` 부터 |
| `doc-sync` 가 어긋났다는데 **문서가 맞다** | 이슈에 라벨을 안 붙인 것이다. `--write` 하지 말고 **이슈에 라벨을 붙인 뒤** 다시 `sync` |
| `표를 찾지 못했습니다` | §작업 보드 표 머리글이 `\| 태스크 \| 상태 \| 담당 \| 이슈 \|` 가 아니게 됐다. 문서는 안 바뀌었으니 표를 되돌리거나 도구를 고친다 |
| 세션에 보드가 안 뜬다 | 캐시가 없으면 훅이 조용히 빠진다. `sync` 후 새 세션 |
| 자동 코멘트가 안 온다 | 워크플로가 `main` 에 있는지, `스탠드업` 라벨 이슈가 열려 있는지 |

## 9. 하지 말 것

- **`.sprint/` 안의 파일을 편집하지 않는다.** 다음 `sync` 에 사라진다. 커밋도 하지 않는다(`.gitignore`)
- **문서 상태 열을 손으로 고치고 끝내지 않는다.** 이슈가 정본이라 다음 `doc-sync` 가 되돌린다
- **이슈와 문서에 같은 설명을 두 번 쓰지 않는다.** 이슈는 무엇을·어디까지, 문서는 왜·무엇이 막혔는지
- **§사용자 작업(U1~U7)을 도구로 갱신하려 하지 않는다.** 진행률 정본은 [#68](https://github.com/duwjd/Branch-out-to-Japan/issues/68) 체크박스다
- **완료를 라벨로 표시하지 않는다.** 이슈를 닫는다
- **GitHub Milestones 를 쓰지 않는다.** 마일스톤은 라벨(`M13`…)로만 표현한다
