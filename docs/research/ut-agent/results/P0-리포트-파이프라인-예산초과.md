# P0 — 진단 리포트가 발행되지 않는다 (콜⑩ 윤문에서 함수 예산 초과)

> 2026-08-20 · UT 파일럿(P5)에서 발견 · 대상 `https://branch-out-to-japan.vercel.app` (`origin/main` 6953e7b)
> 이 발견 때문에 **UT 에서 T3 를 제외**하고 진행하기로 했다(2026-08-20 결정).

## 증상
`POST /api/report` 로 만든 진단 요청이 **한 번도 `published` 에 도달하지 못한다.**
`stage=humanize` 에서 멈춘 뒤, 10분 무갱신 스테일 가드가 `failed`("처리 시간이 초과되었습니다")로 확정한다.

재현: 3/3 (P01 계정 2회 + 더미 계정 1회). 입력은 `personas-input.json` 의 P01 — 상세 콘텐츠 231자(공백 제외), `brandProduct` 모드.

## 실측 (더미 계정, 5초 간격 폴링)

| 경과 | 단계 |
|---|---|
| 11초 | `POST /api/report` → 201 |
| 22초 | `processing / llmCalls` (콜①②③ 병렬 시작) |
| 124초 | `processing / call4` — 콜①②③ 에 **102초** |
| 231초 | `processing / humanize` — 콜④ 에 **107초** |
| 300초 | 함수 상한 — 윤문에 **69초만 남는다** |
| 829초 | `failed` — "처리 시간이 초과되었습니다. 다시 시도해 주세요."(스테일 가드) |

즉 **파이프라인이 윤문에 도달하는 시점에 이미 예산의 77%(231/300초)를 썼다.** 남은 69초 안에
리포트 서술 전체를 되돌려 써야 하는 콜이 끝날 수 없다.

## 원인 — 예산 개념의 비대칭

같은 300초 함수 안에서 도는 두 잡의 설계가 다르다.

| | 상세페이지 잡 | 리포트 잡 |
|---|---|---|
| 시간 예산 | `lib/studio/detail/budget.ts` — `JOB_BUDGET_MS = 270_000`, 조립 여유 30초, 웨이브 단위로 컷 삭감 | **없음** (`reportJob.ts`·`pipeline.ts` 에 budget·deadline·remaining 0건) |
| 예산 부족 시 | 우선순위 낮은 배경컷을 텍스트로 강등하고 **완주** | 그냥 달리다 플랫폼에 죽음 |
| 결과 | 227초에 `done` (파일럿 실측) | 발행 실패 |

여기에 두 가지가 겹친다.

1. **콜 타임아웃이 없다.** `lib/engine/llm/client.ts:149` 의 `messages.create(...)` 에 요청 옵션이 없다 →
   SDK 기본 타임아웃 10분 > 함수 상한 300초. 그래서 `runReportHumanize` 가 이미 갖고 있는
   `catch → skippedReason`(원문 유지 폴백)이 **실행될 기회 자체가 없다.** 폴백이 없어서가 아니라
   폴백에 도달하지 못해서 실패한다.
2. **윤문 출력량이 리포트 본문 전체에 비례한다.** `lib/report/humanizeReport.ts:243` 이
   "고칠 것이 없는 항목도 원문 그대로 포함해 개수를 맞춘다"를 요구하므로, 모델이 서술 문단을
   전부 되돌려 써야 한다. `maxTokens: 12000` 에서 잘리면 `client.ts:267` 이 상향(→16000) 후
   **최대 3회 재시도**한다 — 남은 69초로는 한 번도 끝낼 수 없다.

## 언제 들어왔나
`055bf28 feat(report): 출력 언어 계약 강제 + 모델 상향 + 한국어 윤문 콜⑩` 에서 콜⑩이 신설되고
리포트 모델이 `claude-opus-5`(`client.ts:35`)로 상향됐다. `docs/10-implementation-status.md:146` 은
"Fluid Compute 300초가 파이프라인(2~3분)을 수용"한다고 적고 있는데, 실측은 윤문 진입만 231초다.

※ Fluid Compute 자체는 **켜져 있다.** 꺼져 있으면 60초에 죽으므로 `call4`(124초)에 도달할 수 없다.

## 수정 제안 (스키마 변경 없음 · 3파일)

`humanizeSkipped` 는 이미 1급 개념이다 — `PipelineResult`·화면·`reports.humanize_skipped` 컬럼까지 있다.
새 개념을 만드는 게 아니라 **있는 개념에 도달할 길을 여는** 수정이다.

1. `lib/engine/llm/client.ts` — `StructuredCallOptions` 에 `timeoutMs?: number` 추가,
   `callOnce` 의 `messages.create(params, { timeout })` 두 번째 인자로 전달.
2. `lib/engine/pipeline.ts` — `deps.deadlineAt` 를 받아 윤문 직전에 남은 시간을 재고,
   부족하면(<90초) 건너뛰며 `skippedReason` 을 남긴다. 돌릴 때도 남은 시간 기반 `timeoutMs` 를 준다.
3. `lib/server/reportJob.ts` — `REPORT_BUDGET_MS = 270_000` (상세 잡의 `JOB_BUDGET_MS` 와 같은 규칙)로
   `deadlineAt` 을 만들어 파이프라인에 넘긴다.

효과: 윤문이 늦어도 **리포트는 발행된다**(문체만 원문 유지). 지금은 발행 자체가 안 된다.

## 심각도

## 수정 결과 (2026-08-21 · `fix/report-budget-guard`)

위 제안 3파일에 **콜⑩ 청크 병렬**을 더해 반영했다. 예산 가드만으로는 리포트가 발행되긴 해도
윤문 진입 시 잔여가 39~61초라 콜⑩이 배포본에서 사실상 항상 스킵되기 때문이다 — 방금 만든 콜을
죽은 코드로 두는 수정은 답이 아니다.

### 무엇을 넣었나

| 파일 | 내용 |
|---|---|
| `lib/engine/reportBudget.ts` (신규) | `REPORT_BUDGET_MS = 270_000` · 단계별 벽시계 상한 · `canHumanize` 게이트. ② `budget.ts` 의 ① 대응물 |
| `lib/engine/llm/client.ts` | `timeoutMs`(재시도 포함 총합) → `messages.create(params, { timeout, maxRetries: 0 })`. 시도마다 잔여로 재계산 |
| `lib/engine/pipeline.ts` | `deps.deadlineAt` 수용 · 콜별 상한 주입 · 윤문 예산 게이트 |
| `lib/report/humanizeReport.ts` | 대상 슬롯을 **최대 4청크로 나눠 병렬 호출**. 청크 일부 실패는 그 구간만 원문 유지 |
| `lib/server/reportJob.ts` | `deadlineAt` 생성 + 완료 로그에 `elapsedMs`/`budgetMs` |
| `scripts/run-report.ts` | CLI가 **배포본과 같은 예산으로** 돈다(`--no-budget` 로 해제). 단계별 경과 로깅 |

`maxRetries: 0` 이 핵심이다 — SDK 기본 재시도(2회)는 타임아웃도 재시도해서 `timeout × 3` 이 되고,
`runStructuredCall` 의 `MAX_ATTEMPTS = 3` 까지 곱해지면 최악 9회 왕복이라 상한이 무의미해진다.

### 회귀 방어

`reportBudget.test.ts` 가 **UT 실측 타임라인(콜①②③ 102초 · 콜④ 107초)** 을 전제로 박아 두고,
그 시점 잔여로 윤문 실측(42초)을 담을 수 있는지 검사한다. 예산 여유가 사라지는 변경은
배포 전에 테스트가 먼저 깨뜨린다. `humanizeReport.test.ts` 는 청크 분할과 **부분 실패**
(청크 하나가 죽어도 나머지 채택분을 버리지 않는가)를 고정한다.

### 남는 성질

- **윤문이 늦어도 리포트는 발행된다.** 예산이 모자라면 콜을 걸지 않고 `humanize_skipped` 에
  사유를 남긴 채 발행한다. 발행 자체가 안 되던 상태로는 돌아가지 않는다.
- 콜①·③·④의 기존 폴백(0점 · 일반형 · 축소)도 이제 **도달 가능**하다. 이전에는 함수가 먼저 죽어
  폴백이 한 번도 발동하지 못했다.
- 상한값(`STAGE_CEILING_MS` · `MAX_CHUNKS`)은 확정이 아니라 **실측 갱신 대상**이다.
  모델·effort·슬롯 수가 바뀌면 `npm run report:cli` 로 다시 재고 갱신한다.
